**§14 The Octa-Memory Matrix（八層記憶矩陣）**

**開頭說明**：
```
當這八層全部組建完成，BugEzy 的大腦結構會呈現完美的立體防線。
AI 不再是每次從零開始的臨時工，而是一個有記憶、會成長、
懂業務、知分寸的 AI 開發夥伴。
```

**§14.1 L1 Debug 經驗庫 🔴（動態）**
- 核心作用：10 秒秒殺重複 Bug，省 95% 推理 Token
- 記憶內容：每次 debug 成功後自動記錄：症狀 → 根因 → 修法 → 關鍵檔案
- 實戰範例：「TypeError: Cannot read 'map' of undefined → API 回傳 null 沒有預設值 → 加 ?? [] 防護」
- 下次遇到類似 error → 自動比對歷史 → 直接給修法
- 越用越聰明

**§14.2 L2 專案知識庫 🟡（靜態）**
- 核心作用：讓 AI 擁有整幅地圖，不用每次重複讀取大文件
- 記憶內容：架構文件、引擎清單、API 路由表、已知的坑
- 實戰範例：「這個欄位用 timestamptz 不是 timestamp」→ AI 不會再犯

**§14.3 L3 客服知識庫 🔵（支援）**
- 核心作用：產品內建客服，自動排查環境與安裝問題
- 記憶內容：安裝教學（Extension / MCP / Bridge）、FAQ、操作指南、錯誤排解
- 實戰範例：用戶問「MCP 連不上」→ AI 查 L3 →「最常見原因是 token 過期，請到設定頁重新複製」
- 整合 SKILL.md：靜態手冊 + 動態經驗 = 完整客服

**§14.4 L4 商業邏輯庫 🟢（業務）**
- 核心作用：確保 AI 修 Code 時，數據與業務規則完全正確
- 記憶內容：核心業務規則
- 實戰範例（LottoShare）：
  - 「冷熱門號碼的權重計算，任何時候分母都不能為 0，且勝率加總必須剛好等於 1 (100%)」
  - ENG-27 回傳的 JSON 格式正確（不噴錯），但數據總和 = 1.2 (120%)
  - 沒有 L4 → AI 說「沒有 bug」
  - 有 L4 → AI 說「違反商業規則，權重分配錯誤」→ 主動修正
- 這是 AI 最常犯的錯：程式碼寫對了，但商業邏輯改錯了

**§14.5 L5 外部依賴庫 🔵（環境）**
- 核心作用：分辨是自己的 Bug 還是第三方 API 掛掉
- 記憶內容：外部依賴的脾氣與坑
- 實戰範例：
  - 「第三方開獎數據 API 每天晚上 8:30~8:35 例行維護，回傳 503 屬正常」
  - ENG-12 在 8:32 噴網路錯誤
  - 沒有 L5 → AI：「你的程式壞了！」
  - 有 L5 → AI：「這是 API 維護，不是你的問題。已幫你加上 Retry Circuit Breaker，5 分鐘後自動重試」

**§14.6 L6 資安合規庫 🔴（防禦）**
- 核心作用：防止 AI 寫出有安全性漏洞或密碼外洩的程式碼
- 記憶內容：專案的資安鐵律
- 實戰範例：
  - 「嚴禁將 API_KEY、JWT_SECRET、DB 密碼寫死在代碼中，必須用 process.env」
  - 「使用者的密碼、身分證字號在日誌中必須完全遮蔽」
  - AI 修完 bug 自動「自我審查（Audit）」
  - 發現自己不小心寫死了一個變數 → 立刻自己改掉
  - 確保產出的 PR 100% 符合資安規範

**§14.7 L7 效能帳本庫 🟠（監控）**
- 核心作用：確保修好 Bug 的同時，網站速度不會變慢
- 記憶內容：各引擎正常運作時的效能基準（Baseline）
- 實戰範例：
  - 「正常情況下 ENG-15 大數據機率回歸引擎，單次運算 < 200ms，記憶體 < 128MB」
  - AI 修完 bug → 重啟引擎 → 自動測試比對帳本
  - 發現修完後運算卡了 2000ms（效能衰退 10 倍）
  - → 主動撤回修改 → 嘗試更省記憶體的寫法

**§14.8 L8 團隊協作庫 🟣（流程）**
- 核心作用：自動對接 Git 與團隊分工，PR 寫得比人類更優雅
- 記憶內容：模組負責人（Owner）+ Git 修改歷史
- 實戰範例：
  - 「Core-Algorithm 模組負責人是 Max，任何修改必須 @Max Review」
  - AI 修好 code → 自動發 PR → 完美的 commit message
  - 自動標記 @Max → 附上說明：「本次修改影響 ENG-12，已根據 Max 上週五在 Slack 提到的架構進行優化」

**§14.9 MCP 工具設計**

```
記憶寫入：
  bugezy:memory_save(layer, entry)     → 存入指定層
  bugezy:memory_learn(debug_session)   → debug 完成後自動萃取經驗存入 L1

記憶讀取：
  bugezy:memory_search(query, layers?) → 跨層搜尋相關記憶
  bugezy:memory_get(layer, topic)      → 精準提取指定層的特定主題

自動守衛：
  bugezy:memory_audit(code_diff)       → L6 資安審查
  bugezy:memory_perf_check(metrics)    → L7 效能比對
  bugezy:memory_biz_validate(output)   → L4 商業邏輯驗證
```

**§14.10 自動學習循環**

```
debug 成功
  → L1 自動存入經驗
  → L7 記錄修前修後效能
  → L6 審查修改是否合規
  → L4 驗證商業邏輯是否正確
  → 全通過 → 經驗確認
  → 下次遇到同類 bug → 直接提取 → 越來越快
```


### 🔴 一處必須改的衝突：`bugezy:` 前綴

卡片 §14.9 寫的是 `bugezy:memory_save(...)`、`bugezy:memory_search(...)` 等 7 個工具，**全部帶 `bugezy:` 前綴**。

但這與 **§5 決策 2** 直接衝突——那是 **PM-296 已經定案並寫進同一份文件**的規則：**工具名一律 snake_case、不加 `bugezy:` 前綴**，理由是 MCP 用戶端本來就以 server 名稱做命名空間，再加前綴會出現 `bugezy - bugezy:memory_save` 這種重複。當時 17 個工具名就是為此全部改過一輪、舊 camelCase 零殘留。

照抄的話，同一份規格書的 §5 和 §14 會互相打臉，而且實作時一定有人照 §14 寫出帶前綴的工具。**所以 7 個工具我全部去掉前綴**，並在兩份文件都留了一個綠框說明原稿是什麼、為什麼改。

順帶把工具總數更新：既有 13 ＋ v2 新增 17 ＋ 記憶 7 ＝ **37 個**（`get_live_errors` 不重複計）。§5 附錄原本記的是 30。

### 三個沒定義、但會卡住 Phase A 第一張卡的問題（已標紅框，未自行決定）

寫 §14.11 時發現 Phase A 其實開不了工，缺三個前提：

1. **記憶存在哪裡？** L1／L2／L4 記的都是**使用者原始碼的內容**（業務規則、架構細節、修法片段）。存雲端 Supabase → `/privacy` 必須同步改（`ARCHITECTURE.md §4-15`：隱私政策要對得上程式碼，這條就是 PM-291 被 CWS 退件學到的）；存本機 → 換機、多人協作、L8 團隊共享全都要重新設計。**這決定了 Phase A 的整個資料層。**
2. **L1 跨不跨使用者共享？**「越用越聰明」若指全平台共享，威力最大——但一則經驗裡含著 A 公司的檔名、函式名與修法，被 B 公司的 AI 取用就是**原始碼細節外洩**。若不共享，新用戶的 L1 是空的，第一個月毫無感覺。兩條路的產品體驗差很多。
3. **L6／L7 的「主動撤回修改」由誰執行？** §14.6 寫「立刻自己改掉」、§14.7 寫「主動撤回修改」——這都是**寫入使用者程式碼**。目前 v1／v2 的工具**沒有任何一支會改檔案**，全是唯讀或操作瀏覽器。要不要跨過這條線、要不要有人工確認關卡，是產品層決策，不該由我在規格書裡默默定調。

三題都不影響「把規格寫下來」，所以我照卡片寫完了，只是標記出來。

#### 新增 §14.12 記憶管理

**§14.12.1 AI 與用戶的 CRUD 權限**

MCP 工具擴充：
```
memory_save(layer, entry)      → 寫入
memory_update(layer, id, entry) → 更新（修法進化時覆蓋舊經驗）
memory_delete(layer, id)       → 刪除
memory_search(query, layers?)  → 搜尋
memory_list(layer)             → 列出某層所有記憶
memory_clear(layer)            → 清空某層
memory_export()                → 匯出整個 .bugezy/
memory_import(path)            → 匯入
```

用戶 CLI 管理：
```
bugezy memory list L1           → 列出 Debug 經驗
bugezy memory delete L1 --id=5  → 刪除某條
bugezy memory export            → 匯出備份
bugezy memory import backup.json → 匯入
bugezy memory clear L1          → 清空某層
bugezy memory stats             → 各層容量統計
```

AI 自動更新場景：
```
第一次修 bug → memory_save(L1, { symptom, fix: '加 ?? []' })
三個月後更好的修法 → memory_update(L1, id, { fix: '改用 Zod schema' })
= 記憶會進化，不會停在最初級的解法
```

**§14.12.2 多專案隔離**

`.bugezy/` 跟著專案根目錄走（跟 `.git/` 同層）：
```
C:\projects\
  ├── client-A-ecommerce\
  │   └── .bugezy\         ← A 的記憶
  ├── client-B-hospital\
  │   └── .bugezy\         ← B 的記憶
  └── my-side-project\
      └── .bugezy\         ← 自己的記憶
```

結構：
```
.bugezy/
  config.json              ← 容量上限、淘汰規則
  memory/
    L1-debug.json
    L2-project.json
    L4-business.json
    L5-dependencies.json
    L6-security.json
    L7-performance.json
    L8-team.json
  .gitignore               ← 預設不進 git（含敏感資訊）
```

**§14.12.3 自動切換**

bridge 啟動時：
```
1. 從 CWD 往上找 .bugezy/（跟 git 找 .git/ 一樣）
2. 找到 → 載入該專案記憶
3. 找不到 → 空白記憶 + 提示 bugezy memory init
4. cd 換專案 → 重啟 bridge → 自動切換
```

L1 跨專案共享的部分：
```
A 專案修過 Stripe webhook bug → 匿名化存雲端
B 專案也接 Stripe → 搜尋時從雲端撈到
= 做過的專案越多，新專案上手越快
```

**§14.12.4 容量限制與智慧淘汰**

本機容量（極寬裕）：
```
L1 一條 ≈ 500 bytes → 1000 條 = 500 KB
整個 .bugezy/ 通常 < 10 MB
```

自動淘汰規則：
```
L1：超過 max_entries（預設 2000）→ 淘汰最久沒匹配的
L7：超過 retention_days（預設 90 天）→ 只保留近期基準
```

合併機制：
```
同一個 bug 修過 5 次 → 自動合併成一條最佳實踐
「最初 ?? → 後來 Zod → 最終 middleware 統一處理」
= 記憶濃縮，不只堆積
```

用戶可設上限：
```json
// .bugezy/config.json
{
  "L1_max_entries": 2000,
  "L7_retention_days": 90,
  "auto_merge": true,
  "auto_evict": true
}
```

**§14.12.5 匯出 / 匯入 / 備份**

```
匯出：bugezy memory export → .bugezy-backup-20260816.json
匯入：bugezy memory import .bugezy-backup-20260816.json
用途：換電腦、新同事加入、專案交接
```

注意：匯出不含雲端 L1 匿名經驗（那些本來就在雲端）。

### 🟡 PM-304：規格書新增 §15 — Zone Grid 空間座標系統（AI 自動分區偵測）

**目標**：把網格分區偵測的完整規格寫進 HTML + md 規格書。

**§15 Zone Grid — AI 的空間座標系統**

**§15.1 為什麼需要**

```
圖釘（§7）= 人指路，AI 去查 → 人機合作
Zone Grid = AI 自己有地圖 → AI 自驅動

第三層：人放圖釘 → AI 偵測（被動）
第四層：AI 自己切格子 → 自己掃描 → 自己找到問題（主動）
```

沒有 Zone Grid → AI 收到 error 只知道「頁面有問題」
有 Zone Grid → AI 知道「Cart 區域的第三個按鈕有問題」

**§15.2 智慧分區邏輯（不是固定切格子）**

按 DOM 語意結構自動分區：
```
<header>           → Zone: Header
<nav>              → Zone: Navigation
<main>
  <aside>          → Zone: Sidebar
  <section.products> → Zone: Product List
  <section.cart>   → Zone: Cart
<footer>           → Zone: Footer
<div.chat-widget>  → Zone: Chat Widget
```

分區規則：
```
1. 優先用 HTML5 語意標籤（header/nav/main/aside/footer/section/article）
2. 其次用 role 屬性（role="banner"/"navigation"/"main"）
3. 再次用 class/id 命名推測（.sidebar/.cart/.footer）
4. 最後按視覺位置切（viewport 分象限）
每個 zone 自動命名 + 記錄 CSS selector
```

**§15.3 Zone 健康狀態**

每個 Zone 有獨立的健康狀態：
```
✅ Healthy  — 零錯誤
🟡 Warning  — 有 console.warn 或效能警告
🔴 Error    — 有 uncaught error 或 network fail
⚫ Unknown  — 尚未掃描
```

Error 歸類邏輯：
```
Console error 的 stack trace → 找到觸發的 DOM 元素 → 反查屬於哪個 Zone
Network fail 的觸發源 → 找到發起 fetch 的元素 → 反查 Zone
= 每個 error 都有「地址」
```

**§15.4 Zone 健康時間軸**

```
Cart Zone：
  10:00 ✅ → 10:05 ✅ → 10:10 🔴 → 10:15 🔴 → 10:20 ✅（修好了）
  「10:10 開始出問題，與 10:09 的程式碼變更相關」

Header Zone：
  一直 ✅
  「不用查，省 token」
```

AI 可以比對時間線：
```
程式碼部署時間 + Zone 狀態變化 = 自動定位哪次改動引入了 bug
```

**§15.5 視覺化 — 半透明網格覆蓋層**

AI 自動偵測模式啟動時，頁面上出現覆蓋層：
```
每個 Zone 有：
  - 半透明邊框（正常=綠色淡、異常=紅色閃爍）
  - 左上角區域名稱標籤
  - 右上角錯誤數量 badge（🔴 ×2）
  - 點擊可展開該區域的錯誤詳情
```

覆蓋層不影響頁面操作：
```
pointer-events: none（預設）
用戶可切換：顯示/隱藏覆蓋層
AI 偵測時自動顯示，偵測完可自動隱藏
```

**§15.6 與圖釘的協作**

```
Zone Grid 找到目標 → 自動在問題區域放圖釘 → 深度分析

AI 自動流程：
  1. map_page_zones → 分析頁面結構
  2. watch_zones → 持續監控
  3. Cart Zone 變 🔴 → 
  4. AI 自動呼叫 pin_analyze('section.cart') → 深度分析
  5. 找到根因 → 提出修復建議
  
= 網格負責「哪裡有問題」
= 圖釘負責「問題是什麼」
= 完美分工
```

**§15.7 MCP 工具**

```
分區類：
  map_page_zones(tab_id?)
    → 自動分析 DOM → 回傳 zone 列表
    → [{ zone_id, name, selector, element_count }]

  get_zone_health(tab_id?)
    → 所有 zone 的健康狀態
    → { zones: [...], summary: { healthy: 5, warning: 1, error: 1 } }

  get_zone_errors(zone_id, tab_id?)
    → 某個 zone 的詳細錯誤
    → { zone: 'Cart', errors: [...], network_fails: [...] }

  get_zone_timeline(zone_id, tab_id?)
    → 某個 zone 的健康時間軸
    → [{ time, status, event }]

  watch_zones(tab_id?)
    → 持續監控所有 zone
    → zone 狀態改變時通知 AI（透過下次 MCP 呼叫回傳）
```

**§15.8 與 Bug 嚴重度（§6）整合**

```
Zone 嚴重度繼承最高等級的 error：
  Cart Zone 有 1 個 🔴 Critical + 2 個 🟡 Minor
  → Zone 整體 = 🔴 Critical

AI 行為：
  🔴 Zone → 立即停下來分析這個 Zone
  🟡 Zone → 記錄，階段完成後再看
  ✅ Zone → 跳過，省 token
```

**§15.9 開發順序**

### 🔴 §15.3 的 error 歸類：照字面實作會得到一個永遠回 null 的歸類器

卡片寫：

```
Console error 的 stack trace → 找到觸發的 DOM 元素 → 反查屬於哪個 Zone
Network fail 的觸發源        → 找到發起 fetch 的元素 → 反查 Zone
```

**stack trace 裡沒有 DOM 元素。** 它給的是 `檔名:行:列` 與函式名，瀏覽器沒有任何「這個 stack frame 對應哪個節點」的 API。同樣地，`fetch()` 也沒有「發起它的元素」這種東西——它就是一個全域函式呼叫，跟 DOM 沒有關聯。

這一段是整個 §15 的地基（`get_zone_health`、覆蓋層 badge、`watch_zones`、§15.8 的「✅ 就跳過」全部建立在它之上），所以我沒有照抄，而是**寫成「在錯誤發生的當下抓現場」**，並且四條路徑都對得上這個專案已經有的東西：

| 錯誤來源 | 怎麼拿到元素 | 現況 |
|---|---|---|
| 事件處理器內的錯誤 | 攔截時記下正在派送的 `event.target` | `inject.ts` 已在 MAIN world 攔 console／網路，加掛即可 |
| 資源載入失敗（img／script）| capture 階段的 `error` 事件**本來就帶 `event.target`** | **Day 20 已經在收**，這條最準 |
| fetch／XHR 失敗 | 發起當下的 `document.activeElement` ＋ 最後一次使用者互動的元素 | **rrweb 的互動軌跡已經有這筆資料** |
| setTimeout／模組頂層／Promise 深處 | 抓不到 → 進 `Unassigned` | 見下 |

**必須有一個 `Unassigned`（全域）zone，而且要在 `get_zone_health` 的 summary 裡如實回報數量。** 這點我特別在兩處都寫了：歸不了類的 error 若默默消失，畫面上會是一片令人安心的綠——**而 §15.8 的規則正是「✅ 就跳過，省 token」**。也就是說吞掉的 error 不只是漏報，它會**主動讓 AI 跳過一個其實有問題的頁面**。省 token 的設計和沉默失敗的組合特別危險。

### 另外兩個矛盾與一個漏掉的情境

**① `pointer-events: none` 與「點擊可展開錯誤詳情」直接互斥。** 整層設 `none` 就收不到任何點擊。正解是兩層：外層容器 `none` 讓點擊穿透，只有**名稱標籤與 badge** 設 `auto`。已寫進文件，並附帶提醒這兩顆小元件會擋住底下同位置的頁面元素，要放角落並可關閉。

**② 覆蓋層不能用 `innerHTML` 建。** 啟用 Trusted Types 的網站會直接擋掉字串賦值，結果是覆蓋層整個不出現、只在頁面 console 留一行錯誤——看起來就像功能壞了但查不出原因。**本專案 PM-69 踩過同一個坑**，已在文件裡引 `ARCHITECTURE.md` 標明要用 DOM API。

**③ 卡片沒提 SPA。** 分區規則 1~3 讀的都是當下的 DOM，React／Vue 換頁後 `<main>` 底下整批換掉，舊 selector 全部指向不存在的節點——**`watch_zones` 會安靜地監控一組已經消失的區域，然後回報「一切正常」**。已加註要用 `MutationObserver` ＋ History API 攔截重新分區（兩者 `inject.ts` 都已具備），並提醒重新分區時 `zone_id` 要沿用同名 zone，否則 §15.4 的時間軸每次換頁就斷一截。

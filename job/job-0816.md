**§14 The Octa-Memory Matrix（八層記憶矩陣）**

**開頭說明**：
```
當這八層全部組建完成，BugEzy 的大腦結構會呈現完美的立體防線。
AI 不再是每次從零開始的臨時工，而是一個有記憶、會成長、
懂業務、知分寸的 AI 開發夥伴。
```

**§14.1 L1 Debug 經驗庫 🔴（動態）**
- 核心作用：10 秒秒殺重複 Bug，省 95% 推理 Token
- 記憶內容：每次 debug 成功後自動記錄：症狀 → 根因 → 修法 → 關鍵檔案
- 實戰範例：「TypeError: Cannot read 'map' of undefined → API 回傳 null 沒有預設值 → 加 ?? [] 防護」
- 下次遇到類似 error → 自動比對歷史 → 直接給修法
- 越用越聰明

**§14.2 L2 專案知識庫 🟡（靜態）**
- 核心作用：讓 AI 擁有整幅地圖，不用每次重複讀取大文件
- 記憶內容：架構文件、引擎清單、API 路由表、已知的坑
- 實戰範例：「這個欄位用 timestamptz 不是 timestamp」→ AI 不會再犯

**§14.3 L3 客服知識庫 🔵（支援）**
- 核心作用：產品內建客服，自動排查環境與安裝問題
- 記憶內容：安裝教學（Extension / MCP / Bridge）、FAQ、操作指南、錯誤排解
- 實戰範例：用戶問「MCP 連不上」→ AI 查 L3 →「最常見原因是 token 過期，請到設定頁重新複製」
- 整合 SKILL.md：靜態手冊 + 動態經驗 = 完整客服

**§14.4 L4 商業邏輯庫 🟢（業務）**
- 核心作用：確保 AI 修 Code 時，數據與業務規則完全正確
- 記憶內容：核心業務規則
- 實戰範例（LottoShare）：
  - 「冷熱門號碼的權重計算，任何時候分母都不能為 0，且勝率加總必須剛好等於 1 (100%)」
  - ENG-27 回傳的 JSON 格式正確（不噴錯），但數據總和 = 1.2 (120%)
  - 沒有 L4 → AI 說「沒有 bug」
  - 有 L4 → AI 說「違反商業規則，權重分配錯誤」→ 主動修正
- 這是 AI 最常犯的錯：程式碼寫對了，但商業邏輯改錯了

**§14.5 L5 外部依賴庫 🔵（環境）**
- 核心作用：分辨是自己的 Bug 還是第三方 API 掛掉
- 記憶內容：外部依賴的脾氣與坑
- 實戰範例：
  - 「第三方開獎數據 API 每天晚上 8:30~8:35 例行維護，回傳 503 屬正常」
  - ENG-12 在 8:32 噴網路錯誤
  - 沒有 L5 → AI：「你的程式壞了！」
  - 有 L5 → AI：「這是 API 維護，不是你的問題。已幫你加上 Retry Circuit Breaker，5 分鐘後自動重試」

**§14.6 L6 資安合規庫 🔴（防禦）**
- 核心作用：防止 AI 寫出有安全性漏洞或密碼外洩的程式碼
- 記憶內容：專案的資安鐵律
- 實戰範例：
  - 「嚴禁將 API_KEY、JWT_SECRET、DB 密碼寫死在代碼中，必須用 process.env」
  - 「使用者的密碼、身分證字號在日誌中必須完全遮蔽」
  - AI 修完 bug 自動「自我審查（Audit）」
  - 發現自己不小心寫死了一個變數 → 立刻自己改掉
  - 確保產出的 PR 100% 符合資安規範

**§14.7 L7 效能帳本庫 🟠（監控）**
- 核心作用：確保修好 Bug 的同時，網站速度不會變慢
- 記憶內容：各引擎正常運作時的效能基準（Baseline）
- 實戰範例：
  - 「正常情況下 ENG-15 大數據機率回歸引擎，單次運算 < 200ms，記憶體 < 128MB」
  - AI 修完 bug → 重啟引擎 → 自動測試比對帳本
  - 發現修完後運算卡了 2000ms（效能衰退 10 倍）
  - → 主動撤回修改 → 嘗試更省記憶體的寫法

**§14.8 L8 團隊協作庫 🟣（流程）**
- 核心作用：自動對接 Git 與團隊分工，PR 寫得比人類更優雅
- 記憶內容：模組負責人（Owner）+ Git 修改歷史
- 實戰範例：
  - 「Core-Algorithm 模組負責人是 Max，任何修改必須 @Max Review」
  - AI 修好 code → 自動發 PR → 完美的 commit message
  - 自動標記 @Max → 附上說明：「本次修改影響 ENG-12，已根據 Max 上週五在 Slack 提到的架構進行優化」

**§14.9 MCP 工具設計**

```
記憶寫入：
  bugezy:memory_save(layer, entry)     → 存入指定層
  bugezy:memory_learn(debug_session)   → debug 完成後自動萃取經驗存入 L1

記憶讀取：
  bugezy:memory_search(query, layers?) → 跨層搜尋相關記憶
  bugezy:memory_get(layer, topic)      → 精準提取指定層的特定主題

自動守衛：
  bugezy:memory_audit(code_diff)       → L6 資安審查
  bugezy:memory_perf_check(metrics)    → L7 效能比對
  bugezy:memory_biz_validate(output)   → L4 商業邏輯驗證
```

**§14.10 自動學習循環**

```
debug 成功
  → L1 自動存入經驗
  → L7 記錄修前修後效能
  → L6 審查修改是否合規
  → L4 驗證商業邏輯是否正確
  → 全通過 → 經驗確認
  → 下次遇到同類 bug → 直接提取 → 越來越快
```

### 🔴 一處必須改的衝突：`bugezy:` 前綴

卡片 §14.9 寫的是 `bugezy:memory_save(...)`、`bugezy:memory_search(...)` 等 7 個工具，**全部帶 `bugezy:` 前綴**。

但這與 **§5 決策 2** 直接衝突——那是 **PM-296 已經定案並寫進同一份文件**的規則：**工具名一律 snake_case、不加 `bugezy:` 前綴**，理由是 MCP 用戶端本來就以 server 名稱做命名空間，再加前綴會出現 `bugezy - bugezy:memory_save` 這種重複。當時 17 個工具名就是為此全部改過一輪、舊 camelCase 零殘留。

照抄的話，同一份規格書的 §5 和 §14 會互相打臉，而且實作時一定有人照 §14 寫出帶前綴的工具。**所以 7 個工具我全部去掉前綴**，並在兩份文件都留了一個綠框說明原稿是什麼、為什麼改。

### 三個沒定義、但會卡住 Phase A 第一張卡的問題（已標紅框，未自行決定）

寫 §14.11 時發現 Phase A 其實開不了工，缺三個前提：

1. **記憶存在哪裡？** L1／L2／L4 記的都是**使用者原始碼的內容**（業務規則、架構細節、修法片段）。存雲端 Supabase → `/privacy` 必須同步改（`ARCHITECTURE.md §4-15`：隱私政策要對得上程式碼，這條就是 PM-291 被 CWS 退件學到的）；存本機 → 換機、多人協作、L8 團隊共享全都要重新設計。**這決定了 Phase A 的整個資料層。**
2. **L1 跨不跨使用者共享？**「越用越聰明」若指全平台共享，威力最大——但一則經驗裡含著 A 公司的檔名、函式名與修法，被 B 公司的 AI 取用就是**原始碼細節外洩**。若不共享，新用戶的 L1 是空的，第一個月毫無感覺。兩條路的產品體驗差很多。
3. **L6／L7 的「主動撤回修改」由誰執行？** §14.6 寫「立刻自己改掉」、§14.7 寫「主動撤回修改」——這都是**寫入使用者程式碼**。目前 v1／v2 的工具**沒有任何一支會改檔案**，全是唯讀或操作瀏覽器。要不要跨過這條線、要不要有人工確認關卡，是產品層決策，不該由我在規格書裡默默定調。

三題都不影響「把規格寫下來」，所以我照卡片寫完了，只是標記出來。

#### 新增 §14.12 記憶管理

**§14.12.1 AI 與用戶的 CRUD 權限**

MCP 工具擴充：
```
memory_save(layer, entry)      → 寫入
memory_update(layer, id, entry) → 更新（修法進化時覆蓋舊經驗）
memory_delete(layer, id)       → 刪除
memory_search(query, layers?)  → 搜尋
memory_list(layer)             → 列出某層所有記憶
memory_clear(layer)            → 清空某層
memory_export()                → 匯出整個 .bugezy/
memory_import(path)            → 匯入
```

用戶 CLI 管理：
```
bugezy memory list L1           → 列出 Debug 經驗
bugezy memory delete L1 --id=5  → 刪除某條
bugezy memory export            → 匯出備份
bugezy memory import backup.json → 匯入
bugezy memory clear L1          → 清空某層
bugezy memory stats             → 各層容量統計
```

AI 自動更新場景：
```
第一次修 bug → memory_save(L1, { symptom, fix: '加 ?? []' })
三個月後更好的修法 → memory_update(L1, id, { fix: '改用 Zod schema' })
= 記憶會進化，不會停在最初級的解法
```

**§14.12.2 多專案隔離**

`.bugezy/` 跟著專案根目錄走（跟 `.git/` 同層）：
```
C:\projects\
  ├── client-A-ecommerce\
  │   └── .bugezy\         ← A 的記憶
  ├── client-B-hospital\
  │   └── .bugezy\         ← B 的記憶
  └── my-side-project\
      └── .bugezy\         ← 自己的記憶
```

結構：
```
.bugezy/
  config.json              ← 容量上限、淘汰規則
  memory/
    L1-debug.json
    L2-project.json
    L4-business.json
    L5-dependencies.json
    L6-security.json
    L7-performance.json
    L8-team.json
  .gitignore               ← 預設不進 git（含敏感資訊）
```

**§14.12.3 自動切換**

bridge 啟動時：
```
1. 從 CWD 往上找 .bugezy/（跟 git 找 .git/ 一樣）
2. 找到 → 載入該專案記憶
3. 找不到 → 空白記憶 + 提示 bugezy memory init
4. cd 換專案 → 重啟 bridge → 自動切換
```

L1 跨專案共享的部分：
```
A 專案修過 Stripe webhook bug → 匿名化存雲端
B 專案也接 Stripe → 搜尋時從雲端撈到
= 做過的專案越多，新專案上手越快
```

**§14.12.4 容量限制與智慧淘汰**

本機容量（極寬裕）：
```
L1 一條 ≈ 500 bytes → 1000 條 = 500 KB
整個 .bugezy/ 通常 < 10 MB
```

自動淘汰規則：
```
L1：超過 max_entries（預設 2000）→ 淘汰最久沒匹配的
L7：超過 retention_days（預設 90 天）→ 只保留近期基準
```

合併機制：
```
同一個 bug 修過 5 次 → 自動合併成一條最佳實踐
「最初 ?? → 後來 Zod → 最終 middleware 統一處理」
= 記憶濃縮，不只堆積
```

用戶可設上限：
```json
// .bugezy/config.json
{
  "L1_max_entries": 2000,
  "L7_retention_days": 90,
  "auto_merge": true,
  "auto_evict": true
}
```

**§14.12.5 匯出 / 匯入 / 備份**

```
匯出：bugezy memory export → .bugezy-backup-20260816.json
匯入：bugezy memory import .bugezy-backup-20260816.json
用途：換電腦、新同事加入、專案交接
```

注意：匯出不含雲端 L1 匿名經驗（那些本來就在雲端）。

**§15 Zone Grid — AI 的空間座標系統**

**§15.1 為什麼需要**

```
圖釘（§7）= 人指路，AI 去查 → 人機合作
Zone Grid = AI 自己有地圖 → AI 自驅動

第三層：人放圖釘 → AI 偵測（被動）
第四層：AI 自己切格子 → 自己掃描 → 自己找到問題（主動）
```

沒有 Zone Grid → AI 收到 error 只知道「頁面有問題」
有 Zone Grid → AI 知道「Cart 區域的第三個按鈕有問題」

**§15.2 智慧分區邏輯（不是固定切格子）**

按 DOM 語意結構自動分區：
```
<header>           → Zone: Header
<nav>              → Zone: Navigation
<main>
  <aside>          → Zone: Sidebar
  <section.products> → Zone: Product List
  <section.cart>   → Zone: Cart
<footer>           → Zone: Footer
<div.chat-widget>  → Zone: Chat Widget
```

分區規則：
```
1. 優先用 HTML5 語意標籤（header/nav/main/aside/footer/section/article）
2. 其次用 role 屬性（role="banner"/"navigation"/"main"）
3. 再次用 class/id 命名推測（.sidebar/.cart/.footer）
4. 最後按視覺位置切（viewport 分象限）
每個 zone 自動命名 + 記錄 CSS selector
```

**§15.3 Zone 健康狀態**

每個 Zone 有獨立的健康狀態：
```
✅ Healthy  — 零錯誤
🟡 Warning  — 有 console.warn 或效能警告
🔴 Error    — 有 uncaught error 或 network fail
⚫ Unknown  — 尚未掃描
```

Error 歸類邏輯：
```
Console error 的 stack trace → 找到觸發的 DOM 元素 → 反查屬於哪個 Zone
Network fail 的觸發源 → 找到發起 fetch 的元素 → 反查 Zone
= 每個 error 都有「地址」
```

**§15.4 Zone 健康時間軸**

```
Cart Zone：
  10:00 ✅ → 10:05 ✅ → 10:10 🔴 → 10:15 🔴 → 10:20 ✅（修好了）
  「10:10 開始出問題，與 10:09 的程式碼變更相關」

Header Zone：
  一直 ✅
  「不用查，省 token」
```

AI 可以比對時間線：
```
程式碼部署時間 + Zone 狀態變化 = 自動定位哪次改動引入了 bug
```

**§15.5 視覺化 — 半透明網格覆蓋層**

AI 自動偵測模式啟動時，頁面上出現覆蓋層：
```
每個 Zone 有：
  - 半透明邊框（正常=綠色淡、異常=紅色閃爍）
  - 左上角區域名稱標籤
  - 右上角錯誤數量 badge（🔴 ×2）
  - 點擊可展開該區域的錯誤詳情
```

覆蓋層不影響頁面操作：
```
pointer-events: none（預設）
用戶可切換：顯示/隱藏覆蓋層
AI 偵測時自動顯示，偵測完可自動隱藏
```

**§15.6 與圖釘的協作**

```
Zone Grid 找到目標 → 自動在問題區域放圖釘 → 深度分析

AI 自動流程：
  1. map_page_zones → 分析頁面結構
  2. watch_zones → 持續監控
  3. Cart Zone 變 🔴 → 
  4. AI 自動呼叫 pin_analyze('section.cart') → 深度分析
  5. 找到根因 → 提出修復建議
  
= 網格負責「哪裡有問題」
= 圖釘負責「問題是什麼」
= 完美分工
```

**§15.7 MCP 工具**

```
分區類：
  map_page_zones(tab_id?)
    → 自動分析 DOM → 回傳 zone 列表
    → [{ zone_id, name, selector, element_count }]

  get_zone_health(tab_id?)
```

```
Zone 嚴重度繼承最高等級的 error：
```

### 🔴 §15.3 的 error 歸類：照字面實作會得到一個永遠回 null 的歸類器

卡片寫：

```
Console error 的 stack trace → 找到觸發的 DOM 元素 → 反查屬於哪個 Zone
Network fail 的觸發源        → 找到發起 fetch 的元素 → 反查 Zone
```

**stack trace 裡沒有 DOM 元素。** 它給的是 `檔名:行:列` 與函式名，瀏覽器沒有任何「這個 stack frame 對應哪個節點」的 API。同樣地，`fetch()` 也沒有「發起它的元素」這種東西——它就是一個全域函式呼叫，跟 DOM 沒有關聯。

這一段是整個 §15 的地基（`get_zone_health`、覆蓋層 badge、`watch_zones`、§15.8 的「✅ 就跳過」全部建立在它之上），所以我沒有照抄，而是**寫成「在錯誤發生的當下抓現場」**，並且四條路徑都對得上這個專案已經有的東西：

| 錯誤來源 | 怎麼拿到元素 | 現況 |
|---|---|---|
| 事件處理器內的錯誤 | 攔截時記下正在派送的 `event.target` | `inject.ts` 已在 MAIN world 攔 console／網路，加掛即可 |
| 資源載入失敗（img／script）| capture 階段的 `error` 事件**本來就帶 `event.target`** | **Day 20 已經在收**，這條最準 |
| fetch／XHR 失敗 | 發起當下的 `document.activeElement` ＋ 最後一次使用者互動的元素 | **rrweb 的互動軌跡已經有這筆資料** |
| setTimeout／模組頂層／Promise 深處 | 抓不到 → 進 `Unassigned` | 見下 |

**必須有一個 `Unassigned`（全域）zone，而且要在 `get_zone_health` 的 summary 裡如實回報數量。** 這點我特別在兩處都寫了：歸不了類的 error 若默默消失，畫面上會是一片令人安心的綠——**而 §15.8 的規則正是「✅ 就跳過，省 token」**。也就是說吞掉的 error 不只是漏報，它會**主動讓 AI 跳過一個其實有問題的頁面**。省 token 的設計和沉默失敗的組合特別危險。

### 另外兩個矛盾與一個漏掉的情境

**① `pointer-events: none` 與「點擊可展開錯誤詳情」直接互斥。** 整層設 `none` 就收不到任何點擊。正解是兩層：外層容器 `none` 讓點擊穿透，只有**名稱標籤與 badge** 設 `auto`。已寫進文件，並附帶提醒這兩顆小元件會擋住底下同位置的頁面元素，要放角落並可關閉。

### 🔴 卡片的三處事實錯誤（都對照原始碼查過）

### 🔴 最重要的一件事：卡片的版本會「靜默成功」

卡片給的 content script 邏輯是：

```
const el = document.querySelector(msg.selector)
if (!el) → 回 { error: '找不到元素' }
el.click()
回 { clicked: true, ... }
```

問題在於 **`el.click()` 在下列情況不會拋錯，只是什麼都不會發生**：

| 情況 | `el.click()` 的行為 |
|---|---|
| `disabled` 的 button／input | 靜默無反應 |
| `display:none`、`visibility:hidden`、`opacity:0` | 靜默無反應 |
| 尺寸為 0（不佔版面） | 靜默無反應 |
| 節點沒有 `click()` 方法 | TypeError |

前三種會讓工具**回報 `clicked: true`，而頁面根本沒動**。AI 拿到「點成功了」之後會繼續往下推理——找不到預期的變化，就會開始編造原因，或反覆重試同一個沒用的點擊。**這比直接失敗糟糕得多，因為失敗至少會讓 AI 改變策略。**

所以我在點之前一律先檢查，並把不能點的**原因**講清楚（例如「元素 `#submit` 是 disabled 狀態，點了不會有任何反應」），同時附上找到的 `tag` 與文字，讓 AI 知道它確實找對了元素、只是不能點。

這跟 PM-304 我對 Zone Grid `Unassigned` 的堅持是同一件事：**在一個「AI 依賴回報做決策」的系統裡，沉默的假成功是最貴的失敗模式。**

### 另外四個卡片沒寫的處理

**① 非法選擇器會丟 SyntaxError。** `document.querySelector('a[[[bad')` 直接拋 `SyntaxError`，不是回 `null`。沒接的話整個訊息處理會炸掉，bridge 端收到的是逾時而不是原因。已用 try/catch 包起來回「不是合法的 CSS 選擇器」。

**② 「找不到元素」要給得出下一步。** 只說「找不到」對 AI 沒幫助。錯誤訊息除了帶上 selector（卡片有要求），還加了 hint：**元素可能尚未載入、位於 iframe 內**（content script 只跑在最上層框架，manifest 沒有 `all_frames`）**，或選擇器有誤——可先用 `read_page` 確認**。iframe 這點很容易讓人卡很久，因為 selector 在 DevTools 裡明明找得到。

**③ 先取文字再點擊。** 點擊常常觸發導航，一導航頁面就沒了。`tag` 與 `textContent` 一律**在 `click()` 之前**取好，否則會取到空字串或直接失敗。測試裡有一條專門檢查這個順序（`textContent` 的位置必須早於 `.click()`）。

**④ `tab_id` 的處理抽成共用函式。** 新增 `resolveTargetTab()`：省略 → 當前分頁；指定 → **先 `chrome.tabs.get()` 確認存在**，不存在就明確報錯（規格書 §13.3：絕不默默退回當前分頁，那會讓 AI 在你正在用的分頁上執行原本要在自己分頁跑的操作）。PM-309 的 `read_page` 可以直接用。

另外 `textContent` 除了截 100 字，還先做了空白正規化（`\s+` → 單一空格）——原始 HTML 的縮排會讓 100 字裡有一大半是空白，等於白白浪費截斷額度。

### 🔴 這張卡我裝了 jsdom，因為五個驗收條件我原本一項都驗不到

PM-307／308 還能靠純函式與 MCP schema 驗個大概，但 PM-309 的驗收全部是**輸出內容的品質**（有沒有重複、隱藏元素在不在、selector 能不能用、有沒有超過 50000）——不跑真 DOM 就只能空口說白話。

所以我在 `bridge` 裝了 **jsdom 當 devDependency**（不影響發布的執行期相依），把 **`content.ts` 裡真正的 `extractPageContent` 及其相依函式原封不動抽出來**，用 TypeScript 轉譯後在真實 DOM 上跑。**不是自己搭一個假 DOM 來測自己的假設**——那正是 PM-298 犯過的錯。

> jsdom 不是 Chrome（沒有版面計算，走 `getComputedStyle` 後備路徑而非 `checkVisibility`）。這裡驗的是**演算法**，實際瀏覽器行為仍以端到端為準。若你不想留這個相依，說一聲我移掉。

**結果：它立刻抓到一個我自己寫的洞。**

`describeFormField()` 我有好好遮蔽敏感欄位的 `value=`，但同一行的**標籤**欄位我寫了這個 fallback：

```ts
const label = text || aria-label || (el as HTMLInputElement).value || '';
```

input 沒有文字內容，於是 `label` 退回 `.value` —— **未遮蔽**。實際輸出是：

```
[input#pw] hunter2 type=password value=<已遮蔽：敏感欄位>
[input#tok] sk-secret-abc type=text value=<已遮蔽：敏感欄位>
```

**右邊遮好了，左邊整個漏出去。** 而 `read_page` 的結果是會整份進到 AI context 的——等於把使用者的密碼與 API token 送給第三方，直接違反 `/privacy` 的承諾（`ARCHITECTURE §4-15`）。

修法：表單欄位的 label **絕不退回 `.value`**，改用 `aria-label` → `name` 屬性（`api_token` 這種欄位名本身不是機密，而且對 AI 有用）。已在程式碼註明這個洞是測試抓到的，不是想出來的。

敏感判定**沿用 PM-186 既有的 `SENSITIVE_RECT_SELECTORS`**（password／secret／token／key／card／cvv／`[data-sensitive]`），沒有另立一套定義——兩套定義遲早會漂移。

### 🔴 卡片的 `extractPageContent` 照字面實作會產生垃圾

卡片寫「走 DOM tree，對每個可見元素產出一行 `[tag#id.class] textContent`」。問題是 **`textContent` 包含所有子孫的文字**：

```
[body]  整頁的文字……
[div]   整頁的文字……（again）
[div]   整頁的文字……（again）
[p]     真正屬於這裡的文字
```

一個中等頁面就會產生數十倍的重複，**50000 字元的額度在前幾個元素就被吃光，真正有用的按鈕全部落在截斷線之後**——工具看起來有在運作，實際上回傳的是一坨無用的重複文字。

改成只印 **ownText（直屬文字節點）**，而且**只有 interactive 元素、或本身帶文字的元素才輸出一行**。測試 ①：巢狀三層只有一段文字，輸出就只有一行。

---

### 🔴 驗收條件 2 照字面做也是假的

「interactive 元素有 selector 可直接用於 `click_element`」——但 `[tag#id.class]` 是**描述**不是**唯一選擇器**。`.btn` 可能同時命中十個按鈕，AI 照著點就點錯，而且它無從得知自己點錯了。

所以每個 interactive 元素都另外算一個**經過驗證唯一命中**的 selector（id 優先，否則往上組 `nth-of-type` 路徑），輸出成 `→ click: "..."`。測試裡有一條專門檢查：三個同 class 的元素，產出的 selector 各自 `querySelectorAll().length === 1`。端到端那邊還會**拿 read_page 給的 selector 真的去 click 一次**——那才是這條驗收的真正意思。

---

### 其他實作決定

- **隱藏元素用 `FILTER_REJECT` 跳過整個子樹**，不是逐一 `FILTER_SKIP`：父層看不見，子孫不可能看得見，順便省下大量 `getComputedStyle` 呼叫（大頁面的效能差很多）。優先用 `checkVisibility()`（Chrome 105+），沒有才退回 `getComputedStyle`。
- **邊走邊算長度、到頂就停**，而不是先組完再 `slice`——後者在超大頁面上會先吃掉一大塊記憶體。
- **class 只取前 3 個**：Tailwind 之類的原子式 CSS 一個元素能掛 20 個 class，全印會吃光額度卻沒有資訊量。
- **`<iframe>` 標註出來**而不是靜默略過：content script 只跑在最上層框架（manifest 沒有 `all_frames`），AI 至少要知道「這裡有內容但讀不到」，否則會以為頁面就這樣。
- 縮排表示層級（上限 10 層），讓 AI 看得出結構。

## 四、過程中修掉的一個真產品 bug

把 `bridgeClick` 也放進 jsdom 測之後（PM-308 當時只做了靜態檢查），測試立刻打臉：

**改動檔案**：`extension/src/content.ts`（`bridgeClick` 的可見性判斷）。

### 🔴 卡片寫的做法在 React 網站上會靜默失敗

卡片的執行步驟是：

```
input/textarea → el.value = text，觸發 input + change 事件
```

「要觸發 input/change」這個判斷是對的，**但只做到這樣，React 網站上不會生效**。

React 會在 input 節點上裝一個 **`_valueTracker`**：它用 own property 的 getter/setter 攔截 `.value`，並快取目前的值。流程是：

- `el.value = text` → 打到 **tracker 的 setter** → 快取同步更新成新值
- 接著 dispatch `input` → React 比對「快取 vs 現值」→ **一樣** → 判定沒有變化 → **整個事件被忽略**

結果就是：**畫面上文字出現了，但 React state 完全沒動**，接著送出表單會送出空值。而工具會回報 `typed: true`，AI 從回傳值上完全看不出來 —— 又一個 PM-308 那種「靜默假成功」。

**正解**是透過 **prototype 上的原生 setter** 寫入，繞過 tracker：

```ts
const proto = isTextarea ? HTMLTextAreaElement.prototype : HTMLInputElement.prototype;
Object.getOwnPropertyDescriptor(proto, 'value')?.set?.call(input, text);
input.dispatchEvent(new Event('input',  { bubbles: true }));
input.dispatchEvent(new Event('change', { bubbles: true }));
```

這樣 tracker 的快取會維持舊值，React 一比對就發現不一致，正常處理事件。

**`bubbles: true` 也是必要的**：React 用的是掛在 root 的委派監聽，事件不冒泡就收不到。

測試裡我模擬了一個 React 風格的 tracker，斷言兩件事：**真實值已更新** ＋ **tracker 快取仍是舊的**。

> 寫這條測試時我第一次把期望寫反了（斷言快取應該更新），結果 FAIL —— 但那個 FAIL 正好證明程式是對的：**快取被更新才是壞掉的路徑**。已改成正確的模型。

**根因**：`captureVisibleTab` 需要 `activeTab` 或 `<all_urls>`。BugEzy 只有 `activeTab`，而 **`activeTab` 只在使用者「主動叫用擴充功能」之後才會授予該分頁**（點擴充圖示／快捷鍵／右鍵選單）。**bridge 的呼叫永遠沒有使用者手勢。**

現有的截圖功能之所以一直沒問題，是因為它的觸發路徑本來就是使用者操作（popup／快捷鍵 → content overlay → `CAPTURE_SEGMENT`），手勢天然存在。

**而且變通法比原本設想的更受限：導航會撤銷 `activeTab`。**

所以「請使用者先點一下 BugEzy 圖示」只在這個順序下成立：

```
使用者點圖示 → 直接 take_screenshot        ✅ 可行
使用者點圖示 → navigate_to → take_screenshot ❌ 導航已撤銷授權
```

**結論：出任務模式（AI 自己開背景分頁去跑）裡這支工具基本不可用**，只有偵察模式（使用者剛操作過那一頁）能用。

## 三、這正好印證了規格書 §13.2 當初標記的疑慮

PM-300 撰寫 §13.2 時我列過出任務模式截圖的三條路，並標明「**Phase 1 動工前需實測確認**」：

| 方案 | 當時的評估 | 實測後 |
|---|---|---|
| ① 暫時切過去截圖 | 會搶焦點 | **焦點不是問題，權限才是**（本次採用的方案 B）|
| ② `chrome.debugger` | 需 `debugger` 權限＝重新審核 ＋ 黃色橫幅 | 不變 |
| ③ 獨立視窗 `windows.create({focused:false})` | 當時認為「最划算，需實測」 | **一樣過不了 `activeTab` 這關** |

**實測後可以確定：三條路都繞不開權限。** `captureVisibleTab` 的門檻不在「分頁可不可見」，而在「**有沒有使用者手勢**」——③ 只解決了可見性，沒解決授權。這比規格書當時寫的更明確，**建議回填進 §13.2**。

## 五、實作內容（已完成的部分）

**方案 B 的切換流程**（依 FOX 先前的決策）：目標分頁不是 active 時 → `chrome.tabs.update(tab_id,{active:true})` → 等 400ms render → `captureVisibleTab` → **切回原本的 active tab** → 回傳附 `warning`。

**兩個卡片沒寫但影響很大的決定**：

**① 圖片不塞進 JSON 文字，改走 MCP 原生的 image content。** 卡片的回傳規格是 `{ image_base64, ... }`，但一張全螢幕 PNG 的 base64 動輒數十萬字元，**當成文字回傳會直接灌爆 AI 的 context**，而且用戶端也無法把它當圖片顯示。改為 `content: [{type:'image', data, mimeType}, {type:'text', text: metadata}]`。

**② 工具描述主動把 AI 推向 `read_page`。** §8 把「文字讀 DOM 而非截圖，省 95% token」列為 BugEzy 的差異化重點；描述若寫得中性，AI 會習慣性先截圖，等於自己把優勢丟掉。描述裡明寫「想了解頁面結構請優先用 `read_page`」，並載明截圖的前提條件。

**已驗證的部分**：`pngSize()` 用**真實 PNG 檔**驗過（函式從 `dist/background.js` 抽出，非另抄一份）——

```
  PASS  icon-16.png → 16x16
  PASS  icon-48.png → 48x48
  PASS  icon-128.png → 128x128
  PASS  非 PNG 資料 → 回 0x0（不 crash）
  PASS  空字串 → 回 0x0（不 crash）
```

> 尺寸直接讀 PNG 的 IHDR（前 24 bytes），沒有用 `createImageBitmap` 解整張圖 —— service worker 裡沒有 `Image`，而為了拿寬高去解一張全螢幕 PNG 太浪費。

**MCP schema 也已驗**：`take_screenshot` 已註冊、工具總數 **8**、`tab_id` 可選 integer、描述確實包含引導使用 `read_page` 的字樣。

### 🔴 最重要的一件事：這支工具只看得到最近 30 秒

查 `inject.ts` 才發現，背景緩存是 **`REWIND_WINDOW = 30_000` 的滾動視窗**，每 5 秒裁掉舊資料：

```ts
// 每 5 秒裁掉超過視窗的舊資料（循環 buffer）
bgConsoleLogs = bgConsoleLogs.filter((e) => e.timestamp > cutoff);
```

卡片完全沒提到這件事，但它會直接造成誤判：**AI 打開一個頁面、做了幾件事、過個一分鐘才問「這頁有沒有錯誤？」→ 拿到空陣列 → 判定頁面正常**，而其實載入當下就噴了一堆錯，只是已經被裁掉了。

這跟 PM-304 的 `Unassigned` zone、PM-308 的靜默點擊是**同一類問題**：回傳看起來很正常，但語意跟 AI 的理解不一樣。

處置：回傳固定帶 `window_seconds: 30` 與一句 `note`，工具描述也用**大寫 IMPORTANT** 開頭講明：

> 只涵蓋最近約 30 秒（頁面內的滾動緩存）—— 要抓載入當下的錯誤，請先 `navigate_to`／重新整理再**立刻**呼叫。

---

### 另外三個處理

**① 過濾掉 `level: 'info'`。** 既有 `ConsoleLog` 的 level 有 `warn / error / info`，而 `info` 是 Web Vitals 之類的中性訊息 —— 產品內部本來就把它排除在「即時監控錯誤數」之外（`inject.ts` 的 `consoleProblems` 就是 `filter(level !== 'info')`）。一支叫 `get_browser_errors` 的工具若把它們算成錯誤，會讓「沒有錯誤時回空陣列」這條驗收永遠不成立。

**② 🔴 不回傳 `requestBody` / `responseBody`。** 既有 `NetworkError` 型別帶這兩個欄位，裡面可能有**認證 token 或使用者個資**，而這份結果會整份進到 AI 的 context。卡片要的欄位是 `url / status / method / timestamp`，我只回這些（外加 `duration`），把兩個 body 濾掉。同 PM-309 的考量。

**③ `source` 欄位補預設值。** 既有型別裡 `source` 是**可選**的（來自一般 `console.*` 時會省略），但驗收條件 2 要求每筆都含 `source`。缺的一律補 `'console'`，讓欄位結構穩定。

**沒有 `line` 欄位。** 卡片的回傳規格寫了 `line`，但既有 `ConsoleLog` 型別**沒有這個欄位**，inject 也沒有收。我**沒有硬湊一個出來**（從 message 字串裡剖析行號並不可靠，湊出來的錯誤行號比沒有更糟）。驗收條件 2 只要求 `level / message / source`，這三個都有。若確實需要 `line`，要改的是 inject.ts 的攔截層，範圍比這張卡大。

### 🟡 一個重疊，我沒有自行移除

bridge 端**現在有兩支功能重疊的工具**：PM-297 建的 `get_live_errors`，和這張卡新建的 `get_browser_errors`。兩者都是「即時讀當前分頁的錯誤」，而且 bridge 的 `get_live_errors` 本來就**不讀 R2 快取**（它會直接回一句「請改用雲端 MCP」）。

卡片寫「既有 `get_live_errors` 維持不動（讀 R2 快取）」—— 那句描述**符合 Cloudflare Workers 端的那一支，不符合 bridge 這一支**，所以我判斷不該把它當成「保留 bridge 上的重複工具」的指示，但也不敢直接刪。

折衷處置：**保留工具本體不動**（不刪、行為不變），只把它的描述改成標明「已由 `get_browser_errors` 取代，請優先用那一支」。這樣 AI 不會在兩支之間亂猜，而你要保留或移除都還有空間。

> 這一點值得決策：PM-296 決策 2 選 snake_case 不加前綴的理由之一就是「**工具數量翻倍會稀釋 AI 的選擇準確度**」，留兩支做同一件事正好違反這個原則。建議之後把 bridge 的 `get_live_errors` 刪掉 —— 它尚未 `npm publish`，現在移除成本最低。

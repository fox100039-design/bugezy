🔵 **DONE-398**

**🔴 先講一件會決定這張卡能不能動的事：`mcp_usage` 原本沒有 `user_id` 欄位。**

卡片的兌換邏輯是 `.from('mcp_usage').eq('user_id', userId)`，但 `logMcpUsage()` 寫入時只有 `tool_name` / `tokens_estimated` / `chrome_tokens_estimated` / `report_id` —— **完全沒有使用者維度**。這件事 PM-380 的授權稽核已經標紅過（當時列為「`get_usage_stats` 回的是全站數字」的同一個根因）。

所以照卡片直接實作的話，MCP30 會對**每一個人**都回「查不到 MCP 紀錄」，包括你自己。卡片的驗收條件 5「mcp_usage 表結構確認（確保有 user_id 欄位可查）」問的正是這件事，答案是：**沒有，要先補**。

---

**做了三件事**

**① `logMcpUsage` 開始記 `user_id`**

身分來自 MCP URL 的 `?token=`（`/mcp` 路由每個請求會複製一份帶 token 的 env），用既有的 `verifySessionByToken` 解出 user_id。沒帶 token 的呼叫照舊寫入，不會因此漏記。

🔴 **而且一定要有退路**：`user_id` 欄位要等你跑完 ALTER 才存在，而 PostgREST 對未知欄位是**整筆拒絕**，`logMcpUsage` 的錯誤又是被吞掉的 —— 先部署程式碼再跑 SQL 的話，**全站的 MCP 用量記錄會靜靜地停止寫入，而且沒有任何人會發現**。所以做成「先帶 user_id 試一次，失敗就退回原本的欄位組合」（同 PM-82 對 `allow_screenshot_images` 的處理方式）。

**② 兌換時檢查 MCP 紀錄**

用 `MCP_VERIFIED_CODES = new Set(['MCP30'])` 而不是寫死字串比對，之後要再發同類代碼只要加一行。

**🔴 位置很重要：擺在「重複兌換檢查」之後、「搶名額」之前。** 反過來的話，資格不符的人會先把限量代碼的名額搶走再被拒絕 —— MCP30 雖然不限量，但這段程式碼是所有代碼共用的，順序錯了會傷到 BUZZ100 那類限量碼。

**🔴 查不出來時 fail closed。** `hasMcpUsage` 回 `boolean | null`：`null` 代表「查詢本身失敗」（例如欄位還沒建），這時**不發券**。反過來寫的話，資料庫一出問題就變成人人可領。但訊息要跟「你還沒接 MCP」**分開**（前者回 503「目前無法驗證，請稍後再試」，後者回 403 + 教學連結 + `need_mcp: true` 旗標）—— 混在一起的話，使用者會一直重試自己根本沒做錯的事。

**③ SQL 腳本 `server/mcp30-ticket.sql`**（你要在 Supabase 執行）

包含卡片的 INSERT（加 `ON CONFLICT DO NOTHING`，重跑不會壞）、**卡片沒寫但缺了就不會動的 ALTER**、以及 `user_id` 的索引（兌換是 `WHERE user_id` 的查詢）。附三段驗證 SQL，跑完貼結果就知道成不成功。

---

**⚠ 一個資料面的事實，請先知道再測**

`user_id` 是現在才加的欄位，**先前所有的 MCP 呼叫都沒有留下歸屬**。所以包含你自己在內，**都必須在部署後「再呼叫一次任何 MCP 工具」**，才會產生第一筆可用來驗證資格的紀錄。這不是 bug，是那份資料本來就不存在——沒有辦法回填。

對真實使用者反而是對的：他們的流程本來就是「接上 MCP → 用一次 → 兌換」。

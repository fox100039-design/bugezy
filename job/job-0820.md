---

**做了三件事**

**① `logMcpUsage` 開始記 `user_id`**

身分來自 MCP URL 的 `?token=`（`/mcp` 路由每個請求會複製一份帶 token 的 env），用既有的 `verifySessionByToken` 解出 user_id。沒帶 token 的呼叫照舊寫入，不會因此漏記。

🔴 **而且一定要有退路**：`user_id` 欄位要等你跑完 ALTER 才存在，而 PostgREST 對未知欄位是**整筆拒絕**，`logMcpUsage` 的錯誤又是被吞掉的 —— 先部署程式碼再跑 SQL 的話，**全站的 MCP 用量記錄會靜靜地停止寫入，而且沒有任何人會發現**。所以做成「先帶 user_id 試一次，失敗就退回原本的欄位組合」（同 PM-82 對 `allow_screenshot_images` 的處理方式）。

**② 兌換時檢查 MCP 紀錄**

用 `MCP_VERIFIED_CODES = new Set(['MCP30'])` 而不是寫死字串比對，之後要再發同類代碼只要加一行。

**🔴 位置很重要：擺在「重複兌換檢查」之後、「搶名額」之前。** 反過來的話，資格不符的人會先把限量代碼的名額搶走再被拒絕 —— MCP30 雖然不限量，但這段程式碼是所有代碼共用的，順序錯了會傷到 BUZZ100 那類限量碼。

**🔴 查不出來時 fail closed。** `hasMcpUsage` 回 `boolean | null`：`null` 代表「查詢本身失敗」（例如欄位還沒建），這時**不發券**。反過來寫的話，資料庫一出問題就變成人人可領。但訊息要跟「你還沒接 MCP」**分開**（前者回 503「目前無法驗證，請稍後再試」，後者回 403 + 教學連結 + `need_mcp: true` 旗標）—— 混在一起的話，使用者會一直重試自己根本沒做錯的事。

**③ SQL 腳本 `server/mcp30-ticket.sql`**（你要在 Supabase 執行）

包含卡片的 INSERT（加 `ON CONFLICT DO NOTHING`，重跑不會壞）、**卡片沒寫但缺了就不會動的 ALTER**、以及 `user_id` 的索引（兌換是 `WHERE user_id` 的查詢）。附三段驗證 SQL，跑完貼結果就知道成不成功。

---

**這三個觀察合起來說明了什麼**

**① `logMcpUsage` 本身正常，PM-398 的退路沒有把記錄寫壞。** 呼叫次數從 109 → 110，代表 insert 有成功落地。（這點很重要：如果 ALTER 還沒跑而我又沒做退路，這裡會停在 109 而且**完全沒有錯誤訊息**。）

**② `list_reports` 那一次沒有計入**（109→110 只加了 `get_usage_stats` 自己那一筆）。因為沒有 token 的分支是 `return txt(...)` 而不是 `txtWithTokens(...)` —— 那條路徑本來就不記錄用量。這是既有設計，不是這次改壞的。

**③ 🔴 關鍵：`user_id` 一定是 NULL，所以 `with_user_id` 不可能 ≥ 1。**

`logMcpUsage` 解使用者的唯一來源是 `env.__mcp_session_token`，而它只在 `/mcp` 路由從**網址的 `?token=`** 取得：

```ts
const urlToken = url.searchParams.get('token') || '';
const mcpEnv: Env = { ...env, __mcp_session_token: urlToken };
```

`list_reports` 明確回報「請在 MCP URL 加上 ?token=」，這句話只有在 `env.__mcp_session_token` 是空的時候才會出現 —— 也就是**你的 MCP 連線網址就是 `https://bugezy.dev/mcp`，後面沒有帶 token**。

所以：**不管呼叫幾次雲端 MCP，寫進 `mcp_usage` 的每一筆都是 `user_id = NULL`，MCP30 永遠拿不到。**

---

**⚠ 順帶發現一個相關的缺口（建議另開一張卡）**

`list_reports` 等工具的 token 有兩條來源：URL 的 `?token=` **或**參數 `session_token`。但 **`logMcpUsage` 只看得到前者** —— 它拿不到工具的參數。

也就是說：一個照文件用「參數帶 session_token」的使用者，工具可以正常運作，但**他的用量永遠記不到 user_id，因此永遠拿不到 MCP30**。兩條路徑在這件事上不等價，而且從使用者角度完全看不出差別。

要補的話是把已解出的 token 回填進 `env.__mcp_session_token`（那本來就是每請求一份的副本，寫它是安全的），約三處。**這超出 PM-400 的範圍，等你決定。**

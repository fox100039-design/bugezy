### 🟡 PM-265：活動代碼 + 票券錢包 DB 設計（Supabase）

**目標**：在 Supabase 建立活動代碼系統的資料表，支援公開碼（衝量）和個人碼（任務換票），票券可儲存/啟用/疊加。

---

#### 1. promo_codes 表（代碼定義，FOX 管理）

```sql
CREATE TABLE promo_codes (
  code            VARCHAR(30) PRIMARY KEY,          -- 'FIRSTMONTH' / 'BZ-VID-K8M3X2'
  description     TEXT NOT NULL,                     -- '安裝體驗 1 個月'
  duration_days   INTEGER NOT NULL,                  -- 30 / 60 / 90
  code_type       VARCHAR(10) NOT NULL DEFAULT 'public',  -- 'public' / 'personal'
  max_uses        INTEGER,                           -- NULL = 無限（公開碼）/ 1（個人碼）
  current_uses    INTEGER NOT NULL DEFAULT 0,
  is_active       BOOLEAN NOT NULL DEFAULT true,     -- FOX 可隨時停用
  code_expires_at TIMESTAMPTZ,                       -- NULL = 永不過期
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

ALTER TABLE promo_codes ENABLE ROW LEVEL SECURITY;
-- 無 policy = deny all（§4-6 鐵律，Worker service_role 存取）
```

#### 2. user_tickets 表（用戶的票券錢包）

```sql
CREATE TABLE user_tickets (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id),
  code            VARCHAR(30) NOT NULL REFERENCES promo_codes(code),
  duration_days   INTEGER NOT NULL,                  -- 從代碼帶入
  status          VARCHAR(10) NOT NULL DEFAULT 'SAVED',
                  -- 'SAVED'   = 已兌換儲存，未啟用，不計時
                  -- 'ACTIVE'  = 使用中，倒數計時
                  -- 'USED'    = 已用完（到期）
  activated_at    TIMESTAMPTZ,                       -- 啟用時間（SAVED 時 NULL）
  expires_at      TIMESTAMPTZ,                       -- 啟用後算出（activated_at + duration_days）
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE(user_id, code)                              -- 同帳號同碼只能兌換一次
);

ALTER TABLE user_tickets ENABLE ROW LEVEL SECURITY;
```

**注意**：`UNIQUE(user_id, code)` 限制同碼只能兌換一次。但同一任務可重複做（例如拍第二支影片），FOX 會發不同的個人碼（`BZ-VID-K8M3X2` vs `BZ-VID-P4N7Y1`），所以不衝突。

#### 1. 新增 API 端點

**POST /api/promo/redeem** — 兌換代碼
```
Header: Authorization (登入)
Body: { "code": "FIRSTMONTH" }

驗證流程：
1. 認證（getAuthUserId）
2. 查 promo_codes：code 存在？is_active？未過期（code_expires_at）？
3. 查 max_uses：current_uses < max_uses？（NULL = 無限）
4. 查 user_tickets：此用戶是否已兌換過此碼？（UNIQUE 約束）
5. 全通過 → 插入 user_tickets（status='SAVED'）+ promo_codes.current_uses++
6. 回傳：{ ticket_id, code, duration_days, status: 'SAVED', message: '兌換成功' }

錯誤回傳：
- 代碼不存在 / 已停用 → 400 { error: '無效的活動代碼' }
- 代碼已過期 → 400 { error: '此代碼已過期' }
- 已被搶完 → 400 { error: '此代碼已達兌換上限' }
- 已兌換過 → 409 { error: '你已兌換過此代碼' }
```

**POST /api/promo/activate** — 啟用一張儲存的票券
```
Header: Authorization (登入)
Body: { "ticket_id": "uuid" }

流程：
1. 認證
2. 查 user_tickets：ticket_id 屬於此用戶？status='SAVED'？
3. 計算到期日：
   - 查是否有 ACTIVE 票券或 ECPay 付費到期日
   - 基準日 = MAX(現有到期日, NOW())
   - expires_at = 基準日 + duration_days
   ← 這實現了疊加效果：已有到期日 10/8 → 啟用 30 天 → 到期日 11/7
4. 更新 ticket：status='ACTIVE', activated_at=NOW(), expires_at=計算值
5. 回傳：{ ticket_id, status: 'ACTIVE', activated_at, expires_at }
```

**GET /api/promo/wallet** — 查詢票券錢包
```
Header: Authorization (登入)

回傳：{
  active_ticket: { ticket_id, code, duration_days, expires_at, days_left } | null,
  saved_tickets: [ { ticket_id, code, duration_days, created_at } ],
  saved_count: 2,
  free_until: '2026-11-07T00:00:00Z' | null
}
```

```typescript
async function isActiveUserId(userId: string, env: Env): Promise<boolean> {
  const { data } = await supa(env).from('users')
    .select('plan, day_pass_expires_at')
    .eq('user_id', userId).maybeSingle();
  if (data && isActiveUser(data)) return true;

  // 票券檢查
  const { data: ticket } = await supa(env).from('user_tickets')
    .select('id')
    .eq('user_id', userId)
    .eq('status', 'ACTIVE')
    .gt('expires_at', new Date().toISOString())
    .limit(1)
    .maybeSingle();
  return !!ticket;
}
```

#### ⚠ 卡片流程有個併發漏洞，已補（BUZZ100 這種限量碼會超發）

卡片步驟是「③ 檢查 `current_uses < max_uses` → ⑤ 插票券 + `current_uses++`」，檢查與遞增之間**不是原子操作**：99/100 時兩個請求同時進來會雙雙通過檢查 → 變成 101 人領到限量 100 的碼。

**修法**：PostgREST 不支援 `current_uses = current_uses + 1` 這種欄位運算，改用 **compare-and-swap** —— `update ... set current_uses = 讀到的值+1 where code = X and current_uses = 讀到的值`。併發時只有一個請求會更新到列，其餘讀到新值後重試（上限 5 次）。**先搶名額再發票券**；若發票券失敗則把名額補回（best-effort 補償）。無上限的碼（`max_uses = NULL`）不需 CAS，發券成功後才記次數（純統計）。

其他一併補的防護：
- **啟用併發**：`update ... .eq('status','SAVED')` 當條件，同一張票被連點兩次只會成功一次。
- **越權啟用**：查票券與更新都同時比對 `user_id`，拿別人的 `ticket_id` 會 404。
- **代碼大小寫/空白**：`trim().toUpperCase()`，使用者貼上 `firstmonth ` 也能兌換。
- **不存在與已停用回同一句**「無效的活動代碼」，避免被拿來窮舉探測哪些碼存在。

### 🟡 PM-268：ntfy 即時通知（新用戶 / 兌換 / 啟用 / 付款）

**目標**：重要用戶事件即時推播到 FOX 手機（ntfy app），零成本、零帳號。

---

#### 1. ntfy 推播 helper（`server/src/index.ts`）

```typescript
async function notifyFox(env: Env, title: string, body: string, priority?: number): Promise<void> {
  const topic = env.NTFY_TOPIC;
  if (!topic) return;  // 未設定 → 靜默跳過（正式環境可不設）
  try {
    await fetch(`https://ntfy.sh/${topic}`, {
      method: 'POST',
      body,
      headers: {
        'Title': title,
        'Priority': String(priority ?? 3),  // 3=default, 4=high, 5=urgent
      },
    });
  } catch {
    // ntfy 推播失敗不影響主流程
  }
}
```

**fire-and-forget**：用 `void notifyFox(...)` 呼叫，不 await，不阻塞主流程。

#### 2. 環境變數

```bash
wrangler secret put NTFY_TOPIC
# 輸入：bugezy-fox-<隨機8碼>
```

FOX 手機 ntfy app 訂閱同一個 topic。

在 `Env` type 裡加 `NTFY_TOPIC?: string`。

#### 3. 推播觸發點

| 事件 | 位置 | title | body | priority |
|---|---|---|---|---|
| 新用戶註冊 | `POST /api/auth/session`（新建 user 時） | 🆕 新用戶 | `{email} 剛註冊了 BugEzy` | 4 (high) |

#### 🔴 問題 1：卡片的 `'Title': title` 會**拋例外**，7 則推播沒有一則送得出去

卡片的 header 寫法是 `headers: { 'Title': title }`，但 7 個 title **全都含 emoji/中文**（🆕 新用戶、🎫 代碼兌換…）。HTTP header 值限定 ByteString（latin-1），塞非 ASCII 會**同步拋 TypeError**：

```
Cannot convert argument to a ByteString because the character at index 0
has a value of 55356 which is greater than 255
```

（上面是我實跑 `fetch` 的真實錯誤訊息，見下方驗證。）

更糟的是這個 throw 發生在**建構 fetch 的當下（同步）**，不是在 promise 裡 —— `.catch()` 根本接不到，會往上炸到呼叫端。也就是說**只要 FOX 設了 `NTFY_TOPIC`，登入（createSession）、兌換、付款回調就會開始噴錯**，變成「加了通知反而弄壞主流程」。

**修法**：加 `encodeNtfyHeader()`，非 ASCII 標題用 **RFC 2047 Base64**（`=?UTF-8?B?...?=`，ntfy 官方支援）。body 不受限（走 request body，非 header），維持原樣。

#### 🔴 問題 2：卡片的 `void notifyFox(...)` 在 Workers 上**推播不會送達**

Cloudflare Workers 回應送出後會終止 isolate，**沒被 await 也沒交給 `waitUntil` 的 fetch 會被中斷**——這正是本專案踩過的雷（既有的 `mcp_usage` 側寫就是為此改成 `await`）。但卡片驗收 #4 又要求「**不阻塞主流程**」，純 `await` 會把 ntfy 延遲加到使用者請求上。

**修法**：用 `ctx.waitUntil()` —— 唯一同時滿足「保證送達」+「不阻塞」的做法。回應照常立刻送出，isolate 等推播完成才回收。
- `Env` 加 `__ctx?: ExecutionContext`，在 `fetch()` 入口設 `env.__ctx = ctx`（比照 PM-190 `__mcp_session_token` 的 per-request 慣例）。
- `notifyFox` 回傳 `void`（非 async）→ 呼叫端寫 `notifyFox(...)` 即可，不會產生 floating promise，也不可能誤用成 await。
- 取不到 ctx / ctx 已結束 → 退回 fire-and-forget，最壞只是這則沒送到，絕不影響主流程。

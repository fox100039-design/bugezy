### 🟡 PM-334：Phase 2 PM-G — 圖釘巡察模式（patrol_pins）

**目標**：實作 `patrol_pins(tab_id?)` 工具，讓 AI 一次巡檢所有圖釘，自動逐一 analyze 並回報變化。

---

**bridge 側**（`bridge/src/mcp-server.ts`）：
```
server.tool('patrol_pins', ...)
參數：
  tab_id: z.number().optional()
回傳：{
  patrolled: number,
  results: [{
    pin_id, selector, description, status,
    previous_status, changed: boolean,
    summary: string  // 一句話：「正常」/「從 active → stale」/「新增錯誤」
  }],
  alert_count: number,  // 有變化的圖釘數
  tab_id
}
```

**content script 側**（`extension/src/content.ts`）：
```
case 'BRIDGE_PATROL_PINS':
  1. 取得當前分頁所有圖釘
  2. 逐一執行 analyze_element 邏輯（複用 PM-315 的函式）
  3. 比對上次 last_check 結果，偵測變化：
     - 元素消失 → status: 'stale'
     - visibility 改變 → changed: true
     - 新增 error → changed: true
     - 無變化 → changed: false
  4. 更新圖釘的 last_check + status
  5. 更新視覺覆蓋層顏色
  6. 回傳完整巡檢結果
```

**關鍵細節**：
- 沒有圖釘時回 `{ patrolled: 0, results: [], alert_count: 0 }`（不是 error）
- `previous_status` 讓 AI 知道是惡化還是好轉
- `alert_count` 是快速判斷「需不需要深入看」的指標
- 巡檢順序：按圖釘建立時間排序（先釘的先巡）

**驗收條件**：
1. 有 3 個圖釘時巡檢 → patrolled: 3，每個都有結果
2. 元素消失 → status 變 stale + changed: true
3. 無變化 → changed: false
4. 沒有圖釘 → patrolled: 0
5. 視覺覆蓋層顏色有更新

### 🔴 測試抓到的真 bug：元素消失時圖釘沒有被標成 stale

第一次跑 334-2 的結果是：

```json
{"selector":"#p2","status":"active","previous_status":"active","changed":false,"summary":"🟢 ✅ 可見且可互動"}
```

元素明明已經從 DOM 移除了，巡檢卻回報「正常、無變化」。

**根因**：`pin_analyze` 開頭會呼叫 `pin_element` 確保圖釘存在，而元素找不到時 `pin_element` 回 error，`pin_analyze` 就**直接 return 那個錯誤，完全沒碰到 `pin.status`**。`stale` 的標記原本只發生在 `repositionPins()`（畫覆蓋層時），而巡檢是同步讀 `pin.status`、在 rAF 重畫之前就回傳了。

**這正是最糟的失敗模式**：巡檢的用途就是「幫我盯著這些元素」，而它在元素消失時回報「一切正常」—— AI 會據此認為頁面沒問題。

修法：`pin_analyze` 在找不到元素時，若**已有對應圖釘**就把它標成 `stale` 並寫入 `last_check`，而不是回一個裸錯誤。

---

### 兩個設計決定

- **`alert_count` 數的是「狀態有變」而不是「有問題」。** 一個一直是 warning 的圖釘，不該每次巡檢都觸發警報 —— AI 要判斷的是「跟上次比有沒有惡化」。`previous_status` 也一併回傳，讓 AI 分得出惡化與好轉。
- **巡檢順序明確按 `created_at` 排序**。Map 的插入順序剛好就是建立順序，但依賴這個隱含性質很脆弱（日後任何 re-insert 都會打亂），所以明寫排序。

### 🔴 卡片的 `status: 'resolved'` 在目前的模型裡不存在

卡片的 enum 是 `'all' | 'resolved' | 'stale'`。但 **PM-329 已經把 `resolved` 換成 `warning`** —— 當時的理由是 `resolved` 沒有任何程式路徑會去設定它，而 `pin_analyze` 的結果本質是三級（正常／有疑慮／已消失）。

照字面實作的後果是一個**永遠篩不到東西的過濾器**：AI 呼叫 `clear_pins({status:'resolved'})` 拿到 `cleared: 0`，但**無從得知是「沒有符合的圖釘」還是「這個值根本沒用」**。這跟我前幾張卡一直在防的「靜默無效」是同一類。

處置：`status` 收 `all / active / warning / error / stale`；傳 `resolved` 時**明確報錯**並說明它已被 `warning` 取代、要清掉處理完的圖釘請用 `remove_pin`，同時回傳 `valid_status` 讓 AI 知道能填什麼。zod enum 也同步限制，第一道就擋在 MCP 層。

### 三個實作決定

**① 高亮層與圖釘層分開兩層。** 高亮是短暫的、會自動消失；圖釘是常駐的。混在同一層時，高亮的清除邏輯會把圖釘一起洗掉。高亮層 z-index 比圖釘低一階，讓圖釘蓋在高亮之上。

**② 脈衝動畫用 `CSSStyleSheet` 而不是注入 `<style>` 字串。** 啟用 Trusted Types 的網站會擋掉字串賦值 —— 結果是動畫整個不出現、只在 console 留一行錯誤（PM-69 踩過同一個坑）。舊瀏覽器不支援 `adoptedStyleSheets` 時 try/catch 吞掉，框仍在、只是不閃。

**③ 找不到元素時靜默略過，不拋錯。** 這是純視覺功能 —— 若因為某個元素剛好不在就讓 `click_element` 整個失敗，等於用一個裝飾性功能拖垮真正的工作。測試有一條專門驗這個。

**① shadow DOM 是必要的，不是偏好。** 面板注入的是**任意使用者的網站**。用一般 DOM 的話，對方的 CSS reset（`* { box-sizing }`、`div{...}`）會把面板樣式弄爛；反過來我們的樣式也可能汙染對方頁面。shadow root 是唯一能雙向隔離的做法，再加 `:host{all:initial}` 阻斷繼承。

**② 拖動改的是 `right`/`bottom` 而不是 `left`/`top`。** 面板釘在右下角；用 `left/top` 定位的話，視窗一 resize 面板就會跑到奇怪的位置。

**③ 面板不主動去打擾 inject。** 錯誤數改由 `get_browser_errors` 呼叫時**順手回填**（`lastPanelErrorCount`），面板自己只讀快取。若面板每 10 秒自己去要一次即時錯誤，等於在使用者的每個分頁上都掛一個固定輪詢 —— 成本與干擾都不划算。未查詢過時顯示「未查詢」而不是「0」，避免被讀成「沒有錯誤」。

**④ 效能列顯示的是 FCP 而非 LCP。** LCP 要走非同步的 `PerformanceObserver`（PM-316 的 `buffered:true`），面板是同步渲染的；硬要 LCP 會讓面板每次更新都變成非同步。FCP 用 `getEntriesByType('paint')` 同步就拿得到，且欄位明寫 `FCP` 不寫 `LCP`，不會誤導。

**inject.ts 改動**（MAIN world，已有錯誤攔截）：

在既有的錯誤攔截點加上「現場元素」記錄：

```
1. 事件處理器內的錯誤
   - 攔截時記下 event.target（inject.ts 已在 MAIN world 攔 console/網路）
   - 存入 errorZoneMap: Map<errorId, { element, selector, timestamp }>
```

**歸類函式**（content script 可呼叫）：
```
function classifyErrorToZone(errorId, zones): string {
  const record = errorZoneMap.get(errorId)
  if (!record?.element) return 'Unassigned'
  // 往上走 DOM tree，找到第一個屬於某 zone 的祖先
  let el = record.element
  while (el) {
    for (zone of zones) {
      if (el.matches(zone.selector)) return zone.zone_id
    }
    el = el.parentElement
  }
  return 'Unassigned'
}
```

**驗收條件**：
1. 按鈕 click handler throw error → 歸類到按鈕所在的 zone
2. img 載入失敗 → 歸類到 img 所在的 zone
3. setTimeout 內的 error → 歸入 Unassigned
4. Unassigned 的 error 數量在回傳中可見（不被吞掉）
5. 歸類不影響既有錯誤收集流程（inject.ts 向下相容）

### 🔴 §15.3 的原始設計做不出來，這裡是實際可行的替代

規格書原文是「Console error 的 stack trace → 找到觸發的 DOM 元素」。**stack trace 裡沒有 DOM 元素** —— 它只有 `檔名:行:列` 與函式名，瀏覽器不提供任何「frame → 節點」的 API（PM-304 已查證並寫進 §15.3 紅框）。照字面實作會得到一個永遠回 `null` 的歸類器。

改為**在錯誤發生的那一刻抓現場**，四條路徑分別是：

| 錯誤來源 | 現場元素怎麼來 | 準確度 |
|---|---|---|
| 資源載入失敗（img/script/link）| capture 階段 `error` 事件的 `event.target` **就是**該元素 | 最準 |
| 事件處理器內的錯誤 | capture 階段記下的最後互動元素（click/input/focusin）| 高 |
| fetch / XHR 失敗 | 發起當下的 `document.activeElement` 或最後互動元素 | 中 |
| setTimeout／模組頂層／Promise 深處 | 抓不到 → **Unassigned** | — |

**記的是 selector 字串而不是元素本身**：這筆資料要經 `postMessage` 從 MAIN world 送到 content script，**DOM 節點不可序列化**，直接塞會整包丟失。

歸類時從該 selector 的元素**往上走 DOM tree**，找到第一個符合某 zone selector 的祖先。找不到 → Unassigned。

**`level: 'info'` 不計入錯誤**（Web Vitals 之類），否則「零錯誤」永遠不會成立。

### Pull 模式是唯一可行解，不是妥協

§15.7 綠框②：**MCP 協定沒有 server 主動推播給模型的通道**。所以 `watch_zones` 只在 content script 內定期掃描並**累積**變化，AI 主動呼叫 `get_zone_changes` 時才取走。工具描述用大寫 **PULL-based** 講明，避免 AI 以為啟動後就會自動收到通知而傻等。

**`get_zone_changes` 讀取即清空** —— 語意是「自上次查詢後的變化」。這點也寫進描述，否則 AI 可能以為是「累積清單」而重複處理同一筆。

**未啟動監控時查詢會明確說明**（而不是回一個空陣列）—— 空陣列在這裡有歧義：可能是「沒有變化」也可能是「根本沒在監控」，兩者的下一步完全不同。

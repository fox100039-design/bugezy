## §3 技術架構 — bugezy-bridge（極速模式）

### 架構圖
```
任何 AI（Claude / ChatGPT / Cursor / Gemini）
    │
    MCP 標準協議
    │
bugezy-bridge（localhost Node.js）
    │
    Chrome Native Messaging
    │
BugEzy Extension（content.ts）
    │
    目標網頁
```

### 安裝方式
```bash
npm install -g bugezy-bridge
```

### 運作方式
- bugezy-bridge 跑一個 localhost MCP server
- 透過 Chrome Native Messaging 連接 Extension
- AI 呼叫 MCP → bridge 轉發給 Extension → 拿結果回傳
- 延遲 < 50ms
- 全部在用戶電腦上跑，BugEzy 伺服器成本 = 0

## §4 技術架構 — 雲端模式（WebSocket）

### 架構圖
```
任何 AI
    │
    MCP 標準協議
    │
Cloudflare Workers
    │
    WebSocket（Durable Objects）
    │
BugEzy Extension
    │
    目標網頁
```

### 運作方式
- Extension 啟動時建立 WebSocket 長連線
- AI 呼叫 MCP → Workers 透過 WebSocket 推給 Extension
- 延遲 ~200ms
- 用戶零安裝成本

## §6 Bug 嚴重度分類

### 自動判定規則
| 嚴重度 | 條件 | AI 行為 |
|---|---|---|
| 🔴 Critical | Uncaught Error / TypeError / ReferenceError | 立即中斷，馬上修 |
| 🔴 Critical | Network 500 | 立即中斷 |
| 🔴 Critical | Promise rejection 未處理 | 立即中斷 |
| 🟡 Minor | Console.warn | 記錄，稍後處理 |
| 🟡 Minor | Network 404 | 記錄，稍後處理 |
| 🟡 Minor | Web Vitals 超標 | 記錄，稍後處理 |
| ⚪ Info | console.log / info | 忽略 |

### MCP 回傳格式
```json
{
  "critical": [{ "type": "TypeError", "message": "...", "file": "cart.js", "line": 42 }],
  "minor": [{ "type": "warning", "message": "..." }],
  "summary": "🔴 1 critical, 🟡 2 minor"
}
```

### 用戶可自訂規則
- /api/ 開頭的 404 → 升級為 🔴
- 含 'deprecated' 的 warn → 降級為 ⚪

## §7 AI Debug 視覺化

### 藍框巡察動畫
- AI 操作/偵測時，頁面上出現藍色方框
- 方框移動到 AI 正在檢查的元素位置
- CSS transition 平滑移動（300ms）
- 呼吸光暈效果表示「檢查中」

### 圖釘狀態顏色
| 顏色 | 狀態 |
|---|---|
| ⚪ 白色 | 剛放上去，等待檢查 |
| 🔵 藍色 | AI 正在檢查中 |
| ✅ 綠色 | 檢查完畢，沒問題 |
| ⚠ 橘色 | 輕微問題 |
| 🔴 紅色 | 嚴重問題 |

- AI 按順序巡察：藍框跑到 ① → 檢查 → 變色 → 跑到 ② → ...
- 每個圖釘旁浮出小標籤：「正在分析 DOM 結構...」

### 🟡 PM-297：bugezy-bridge 骨架 — localhost MCP Server + Extension 通訊

**目標**：建立 `bugezy-bridge`，一個跑在用戶電腦上的 Node.js 程式，讓任何 AI 透過 MCP 即時操作瀏覽器。這是 v2 的地基。

**產出**：`bridge/` 目錄（新建，在 `C:\dev\bugezy\bridge\`）

---

#### 1. 整體架構

```
任何 AI（Claude / ChatGPT / Cursor）
    │
    MCP 標準協議（stdio 或 HTTP）
    │
bugezy-bridge（localhost Node.js）
    │
    與 Extension 通訊（見下方方案）
    │
BugEzy Extension（content.ts / background.ts）
    │
    目標網頁
```

#### 2. bugezy-bridge 的職責

```
1. 啟動一個 MCP Server（讓 AI 連接）
2. 接收 AI 的指令（navigate_to, click_element, read_page 等）
3. 轉發指令給 BugEzy Extension
4. 等待 Extension 回傳結果
5. 回傳結果給 AI
```

#### 3. Extension 與 bridge 的通訊方式

**請評估以下三種方案，選最適合的實作：**

**方案 A：Native Messaging**
```
Extension ←→ chrome.runtime.connectNative('bugezy_bridge')
優點：Chrome 原生支援，穩定
缺點：需要 OS 註冊 host manifest、加 nativeMessaging 權限（會觸發重新審核）
```

**方案 B：localhost WebSocket**
```
bridge 開 WebSocket server（ws://localhost:PORT）
Extension 的 service worker 連上
優點：不需要 nativeMessaging 權限、不觸發審核
缺點：需要確認 Extension service worker 能連 localhost WebSocket
```

**方案 C：localhost HTTP 輪詢**
```
bridge 開 HTTP server（http://localhost:PORT）
Extension 每 500ms 輪詢 GET /commands
拿到指令 → 執行 → POST /results
優點：最簡單、最穩定、不需要任何新權限
缺點：延遲 ~500ms（但對 debug 來說夠快）
```

**選擇原則**：
- 不觸發 Chrome Web Store 重新審核為最優先（v1.1.5 還在審核中）
- 延遲 < 1 秒可接受
- 穩定性 > 速度

#### 4. MCP Server 規格

使用 `@modelcontextprotocol/sdk` 建立 MCP server。

**第一版只註冊 3 個工具（驗證通訊通道用）：**

```typescript
// 工具 1：ping — 測試連線
server.tool('ping', {}, async () => {
  // 送指令給 Extension → Extension 回 pong → 回傳
  return { status: 'ok', latency_ms: 42, extension_connected: true };
});

// 工具 2：get_page_url — 取得當前分頁 URL
server.tool('get_page_url', {}, async () => {
  // 送指令給 Extension → Extension 讀 tab URL → 回傳
  return { url: 'https://example.com/cart', title: 'Shopping Cart' };
});

// 工具 3：get_live_errors — 取得即時 Console errors
server.tool('get_live_errors', { source: { type: 'string', default: 'browser' } }, async () => {
  // 送指令給 Extension → Extension 讀 console → 回傳
  return { errors: [...], count: 3 };
});
```

### 🔴 通訊方案：選 B（localhost WebSocket）

卡片列的「缺點」低估了 C 的問題，這裡把判斷寫清楚：

| 方案 | 判斷 |
|---|---|
| **A　Native Messaging** | ❌ 需要 `nativeMessaging` 權限 → **觸發 Chrome Web Store 重新審核**，而 v1.1.5 還在審。違反卡片的最優先原則。 |
| **C　HTTP 輪詢 500ms** | ❌ **不是「延遲 500ms」而已，是根本撐不過 MV3**：service worker 閒置 30 秒就被回收，`setInterval` 隨之消失，**而且沒有任何事件能把它喚醒** → 半分鐘後靜默失效。`chrome.alarms` 最短 30 秒，無法做 500ms 輪詢。另外長年輪詢會白耗每位使用者的 CPU。 |
| **B　localhost WebSocket** | ✅ **選這個**。WebSocket 不受 CORS 限制、連 localhost **不需要任何新權限**；且 **Chrome 116 起 WebSocket 活動會重置 service worker 的閒置計時器**——每 20 秒一次心跳就是官方認可的保活方式。延遲 <50 ms（實測 8 ms）。 |

換句話說：**B 不只比 C 快，而是 C 在 MV3 下根本不可靠**，而 B 剛好是 Chrome 官方文件給的 service worker 保活解法。這也同時滿足「穩定性 > 速度」與「不觸發審核」兩個原則。

### 🔴 缺陷 1：`get_page_url` 回空字串（我自己的假測試給了假綠燈）

**修法（不加任何權限）**：改問 content script。宣告式 content script 本來就注入在每個頁面，直接讀 `location.href` / `document.title` 不需要任何權限。新增 `GET_PAGE_INFO` 訊息（`content.ts` + `types.ts` 型別聯集）。

```
bridge 關閉 → WebSocket 斷線 → 沒有 WS 活動 → SW 閒置 30 秒被殺
           → 重連的 setTimeout 一起消失 → 沒有任何事件會喚醒它 → 永遠不會重連
```

**這正是我在 PM-297 用來否決「HTTP 輪詢」方案的同一個坑，只是換個位置又出現一次。**

**正解**是 `chrome.alarms`（能喚醒已被回收的 SW），但那要新增 `alarms` 權限 → **觸發 Chrome Web Store 重新審核**，違反本階段「不加新權限」的硬條件。

**改採搭便車**：在 SW 本來就會被喚醒的事件上順手確保連線——`onMessage`（popup／content script 來訊）、`onStartup`、`onInstalled`、`tabs.onActivated`、`tabs.onUpdated`（後兩者不需 `tabs` 權限也會觸發）。

### 順帶補上的三個實作陷阱（卡片未提，但會直接卡住 Phase 1）

寫 §13.2「`active: false` 不搶焦點」時發現這句話有前提沒說：

1. **`take_screenshot` 截不到背景分頁**。`chrome.tabs.captureVisibleTab()` 只截「該視窗當前**可見**的分頁」。三條路：① 切過去（**會搶焦點，違背整個模式的前提**）② `chrome.debugger` 的 `Page.captureScreenshot`（**需 `debugger` 權限＝重新審核**，且畫面上方會常駐黃色偵錯橫幅）③ **改開獨立視窗** `chrome.windows.create({focused:false})`——AI 的分頁在那個視窗裡就是「可見分頁」，`captureVisibleTab` 可用且不搶焦點。**③ 看起來最划算，但動工前要實測。**
2. **背景分頁會被 Chrome 節流**（計時器降頻、久了甚至凍結）。以「跑完一段流程」為目標的自動化，等待與逾時不能沿用前景分頁的直覺。獨立視窗方案同樣能緩解。
3. **共享 session 是雙面刃**：登入狀態自動繼承很方便，但也代表 **AI 是以你的真實身分在操作真實帳號**。送出訂單、刪資料、寄信這類動作必須有防線——已標記留給 v3 安全設計。

### 補上的東西：這兩類是**有狀態**的，跟前面九個不一樣

操作類與偵測類都是「問一次答一次」，加 `tab_id` 就只是換個對象。但圖釘和監控**會在分頁上留下持續存在的狀態**，所以光加參數不夠，還得定義狀態怎麼隔離、怎麼收掉。兩份文件都補了三條：

1. **每個分頁各自一份**。同時對多個分頁 `start_monitor()` 要能各自獨立運作。
2. **🔴 `stop_monitor()` 省略 `tab_id` 時只停當前分頁，不可一次停光全部。** 這條最要緊——否則 AI 在偵察模式下隨手停一次監控，會把出任務模式跑到一半的監控一起殺掉，而且**不會有任何錯誤訊息**，只會得到一份莫名其妙不完整的報告。
3. **分頁關閉時必須自動收斂**（自動 `stop_monitor` + 釋放該分頁的圖釘狀態），否則出任務模式跑完關掉分頁，就留下一個永遠不會結束的監控。

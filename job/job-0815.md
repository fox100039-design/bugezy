## §3 技術架構 — bugezy-bridge（極速模式）

### 架構圖
```
任何 AI（Claude / ChatGPT / Cursor / Gemini）
    │
    MCP 標準協議
    │
bugezy-bridge（localhost Node.js）
    │
    Chrome Native Messaging
    │
BugEzy Extension（content.ts）
    │
    目標網頁
```

### 安裝方式
```bash
npm install -g bugezy-bridge
```

### 運作方式
- bugezy-bridge 跑一個 localhost MCP server
- 透過 Chrome Native Messaging 連接 Extension
- AI 呼叫 MCP → bridge 轉發給 Extension → 拿結果回傳
- 延遲 < 50ms
- 全部在用戶電腦上跑，BugEzy 伺服器成本 = 0

## §4 技術架構 — 雲端模式（WebSocket）

### 架構圖
```
任何 AI
    │
    MCP 標準協議
    │
Cloudflare Workers
    │
    WebSocket（Durable Objects）
    │
BugEzy Extension
    │
    目標網頁
```

### 運作方式
- Extension 啟動時建立 WebSocket 長連線
- AI 呼叫 MCP → Workers 透過 WebSocket 推給 Extension
- 延遲 ~200ms
- 用戶零安裝成本

## §6 Bug 嚴重度分類

### 自動判定規則
| 嚴重度 | 條件 | AI 行為 |
|---|---|---|
| 🔴 Critical | Uncaught Error / TypeError / ReferenceError | 立即中斷，馬上修 |
| 🔴 Critical | Network 500 | 立即中斷 |
| 🔴 Critical | Promise rejection 未處理 | 立即中斷 |
| 🟡 Minor | Console.warn | 記錄，稍後處理 |
| 🟡 Minor | Network 404 | 記錄，稍後處理 |
| 🟡 Minor | Web Vitals 超標 | 記錄，稍後處理 |
| ⚪ Info | console.log / info | 忽略 |

### MCP 回傳格式
```json
{
  "critical": [{ "type": "TypeError", "message": "...", "file": "cart.js", "line": 42 }],
  "minor": [{ "type": "warning", "message": "..." }],
  "summary": "🔴 1 critical, 🟡 2 minor"
}
```

### 用戶可自訂規則
- /api/ 開頭的 404 → 升級為 🔴
- 含 'deprecated' 的 warn → 降級為 ⚪

## §7 AI Debug 視覺化

### 藍框巡察動畫
- AI 操作/偵測時，頁面上出現藍色方框
- 方框移動到 AI 正在檢查的元素位置
- CSS transition 平滑移動（300ms）
- 呼吸光暈效果表示「檢查中」

### 圖釘狀態顏色
| 顏色 | 狀態 |
|---|---|
| ⚪ 白色 | 剛放上去，等待檢查 |
| 🔵 藍色 | AI 正在檢查中 |
| ✅ 綠色 | 檢查完畢，沒問題 |
| ⚠ 橘色 | 輕微問題 |
| 🔴 紅色 | 嚴重問題 |

### 圖釘巡察模式
- 用戶放置多個圖釘並指定順序
- AI 按順序巡察：藍框跑到 ① → 檢查 → 變色 → 跑到 ② → ...
- 每個圖釘旁浮出小標籤：「正在分析 DOM 結構...」

### 三項決策的落地

#### 決策 1：`get_live_errors` 加 `source` 參數
`source='cache'`（預設，讀 R2 快取）／`source='browser'`（v2 新增，即時讀瀏覽器）。

**兩份文件都補了一個實作要點**：bridge 未安裝或連不上時，`source='browser'` 應**自動退回 cache 並在回應中註明**，而不是報錯——這正是選這個方案而非「改名並存」的理由，不寫下來的話實作時很容易做成拋錯。

**🔴 順帶處理一個決策清單沒涵蓋的工具**：卡片給的 17 個 snake_case 名稱裡，**沒有 `getNetworkFails` 的對應名**。查證後發現這不是遺漏而是自然的結果——既有 `get_live_errors` 的工具描述本來就是「取得某使用者當前頁面的即時 **Console/Network** 錯誤」，**本來就同時涵蓋兩者**，另開一支 `get_network_fails()` 會功能重疊。所以我依決策 1 的同一邏輯把它**併入 `get_live_errors`**，並在兩份文件都標明「此為推得，若你仍想拆成獨立工具說一聲即可改」。

#### 決策 2：全 snake_case、不加前綴
17 個工具名全部改完（HTML 與 md **各 17/17 命中，舊 camelCase 名零殘留**）。§11.2 的三個終端機工具也一併去掉 `bugezy:` 前綴。文件中僅存的 `bugezy:` 出現在「為什麼不用前綴」的說明裡。

順帶算了個數字寫進 A-2：v2 完成後 MCP 共 **13 + 17 = 30 個工具**（`get_live_errors` 不重複計）。

#### 決策 3：v2 功能只給訂閱用戶
§2 定價表加入「票券 / 日票」列並標明**不含 v2 功能**；五個層級的「功能」欄改為「可用範圍」，明確標出 v1／v2／v3 的分界。

**🔴 這個決策有個不明顯但重要的後果，我把它寫進文件並調整了開發順序**：

> 既然 v2 功能要擋住票券／日票用戶，**每一個 v2 的 MCP 工具都需要方案等級判斷**。而 `isActiveUserId()` 目前只回傳布林值，分不出「票券用戶」與「Pro 訂閱者」。
> → **分層閘門從 Phase 6 的收尾，變成 Phase 1 的前置**。已在 §9 Phase 1 增列 **PM-B2（方案等級判斷雛形）**，並把 PM-P 改為「方案分層完整上線（Max / Agent）」。

若不先做這個，Phase 1 的工具會對所有付費身分一視同仁，等 Phase 6 才回頭加閘門就得改動每一支工具。
